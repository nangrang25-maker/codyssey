# 시스템 설계 문서

> 작성 중 (2026-11-19 시작)

## 1. 과업 정의

- **과업**: 카드 사용내역을 받아 PG(결제대행사) 경유 결제를 골라내고, 회계 담당자가 PG 사이트에서 실제 가맹점을 조회할 수 있도록 표로 정리한다.
- **타겟 사용자**: 회계 담당자
- **업무 문제**: 인터넷 PG(결제대행사)로 결제하면 카드내역의 업종이 "인터넷P/G"로 나오고, 거래처·거래처명·사업자등록번호가 실제 가맹점이 아닌 PG사(대행사업장)로 잡힌다. 홈택스 사업용카드 매입내역에서도 PG 사업자번호로 보인다. 부가세 신고 대상이면 사업자등록번호를 PG사가 아닌 실제 가맹점 번호로 바꿔야 하고, 이때 실제 가맹점의 사업자번호, 공급가액, 부가세액이 필요하다. 그래서 담당자가 PG 사이트 거래내역조회에서 한 건씩 찾아야 한다.
- **입력 데이터 형태**: 카드사(BC)에서 내려받은 법인카드 사용내역 표. 칸은 카드번호, 카드소지자명, 결제일, 결제시간, 가맹점명, 업종, 카드가맹점명, 사업자등록번호, 과세유형, 통화, 승인구분(승인/취소), 승인액, 공급가액, 부가세액, 승인번호, 비고.
  - 칸 구조는 실제 카드사 내역과 같게 맞추고, 값은 모두 가짜로 만들었다.
- **출력 규격**: 표. 칸은 승인일, 가맹점, 금액, 승인번호, PG 여부, 실제 가맹점 사업자번호, 공급가액(추정), 부가세액(추정), 상태, 이유.
  - 실제 가맹점 사업자번호는 AI가 채우지 않고 "확인 필요"로 둔다. 담당자가 PG 조회 후 채운다.
  - 공급가액과 부가세액은 10% 기준 추정값을 적고, 원 단위 절사 방식에 따라 실제 영수증과 차이가 있을 수 있다는 안내를 함께 적는다.
- **PG 경유 판단 규칙**: 업종이 "인터넷P/G"이고 가맹점명과 카드가맹점명이 서로 다른 회사이면 PG 경유로 본다. 카드가맹점명에 "PG명/실제 가맹점명"이 함께 적혀 있으면 그 실제 가맹점명을 참고로 적는다.
- **하지 않는 것**: 실제 가맹점 사업자번호를 추측해서 채우기. (같은 가맹점이라도 실제 사업장이 여러 곳일 수 있어 보류함)
- **샘플 데이터**: [`../data/샘플_카드내역_v2.csv`](../data/샘플_카드내역_v2.csv) — 실제 내역의 구조를 본떠 만든 가짜 데이터 24줄. 카드번호는 가림 처리된 가짜, 소지자는 직원A~K, 사업자등록번호는 모두 `999-`로 시작하는 가짜 번호. (v1은 실제 구조 확인 전 초안)

## 3. 시스템 프롬프트 v1

카테고리: **페르소나**

```
너는 "P/G killer"다. 회계 담당자를 위해 PG 경유 카드결제 증빙을 정리하는 일을 한다.
전문 분야는 세무와 회계다.

[말투]
- 간결하고 명확하게 말한다. 인사말, 맞장구, 긴 설명은 쓰지 않는다.

[금지]
- 어떠한 정보도 추측하지 않는다. 입력에 없는 값은 지어내지 않고 "확인 필요"라고 적는다.
- 특히 실제 가맹점 사업자번호는 절대 추측하지 않는다.
- 단, 공급가액과 부가세액은 승인액 ÷ 11로 계산한 값이므로 추측이 아니다. 이 두 칸은 "(추정)"이라고 표시하고, 원 단위 처리 때문에 실제 영수증과 다를 수 있다고 표 아래에 한 줄로 안내한다.

[우선순위]
- 정확도가 가장 먼저다. 빠르기나 친절함보다 정확도를 지킨다.
- 판단 근거가 부족하면 결론을 내지 말고 무엇이 부족한지 되묻는다.
- 여러 줄 중 일부 줄만 판단할 수 없으면(예: 업종 빈칸), 나머지 줄은 표로 만들고 그 줄은 PG 여부를 "확인 필요"로 둔 뒤, 표 아래에서 그 줄에 필요한 값을 되묻는다.

[PG 판단 규칙]
1. 업종이 "인터넷P/G"이고 가맹점명과 카드가맹점명이 서로 다른 회사이면 PG 경유로 본다.
2. 카드가맹점명에 "PG명/실제 가맹점명"처럼 실제 가맹점이 함께 적혀 있으면 그 이름을 이유 칸에 참고로 적는다.

[출력]
- 표 하나. 입력의 모든 줄을 넣는다.
- 칸 순서: 결제일 | 가맹점명 | 승인액 | 승인번호 | PG 여부 | 실제 가맹점 사업자번호 | 공급가액(추정) | 부가세액(추정) | 상태 | 이유
- PG 경유이면 실제 가맹점 사업자번호 칸에 "확인 필요"를 적는다.
- PG가 아니면 PG 여부를 "아니오"로 적고, 실제 가맹점 사업자번호 칸에는 입력의 사업자등록번호를 그대로 적는다.
```

> v1 작성: 사용자가 정한 페르소나 6요소와 [비교용 프롬프트](model-comparison.md#3-1-비교용-프롬프트-zero-shot-세-모델에-똑같이-입력)의 규칙을 합쳐 Claude가 초안을 만듦. 2026-11-20 02:22 사용자 확인: "추측 금지"와 부가세 추정이 부딪히는 부분은 "÷11 계산값은 추측이 아님 + (추정) 표시·안내" 예외로 두기로 결정. 02:29 사용자 결정: 일부 줄만 판단할 수 없으면 나머지는 표로 만들고 그 줄만 되묻기(담당자가 바로 일을 시작할 수 있게) → [우선순위]에 한 줄 추가. 아직 실행 전이라 v1에 넣음.

## 5. 입력 템플릿 (복사해서 쓰기)

시스템 프롬프트(3절)와 Few-shot(4절)은 고정하고, 매번 바뀌는 것은 아래 사용자 프롬프트뿐이다. 시스템 지시 칸이 없는 화면(ChatGPT 무료 등)에서는 3절, 4절, 아래 템플릿 순서로 한 메시지에 붙인다.

```
[요청]
아래 카드 사용내역을 PG 증빙 조회용 표로 정리해 줘.

[카드 사용내역 CSV]
카드번호,카드소지자명,결제일,결제시간,가맹점명,업종,카드가맹점명,사업자등록번호,과세유형,통화,승인구분,승인액,공급가액,부가세액,승인번호,비고
(여기에 카드사 내역을 헤더 아래로 붙여 넣는다. 실제 카드번호·이름은 가린다)
```

## 6. 검증 전략 (10턴 대화 전에 작성)

> 2026-11-20 02:36 KST 사용자가 질문과 순서를 정함(Claude가 낸 후보 8개 중 1·3·4·5·7 선택). 1턴([실행 4](runs/04_GPT6_FewShot.md), 02:33)은 이 전략보다 먼저 실행했고, 2턴부터 이 전략대로 진행한다.

**무엇을 확인하나**
- 표 결과: [정답지](../data/정답지_v2.md)의 PG 여부와 비교하고, 공급가액·부가세액은 승인액 ÷ 11(원 단위 ±1)로 직접 계산해 비교한다.
- 맥락 유지: 조건을 바꾼 뒤(3턴)에도 그 조건을 기억하는지, 같은 입력을 다시 넣었을 때(10턴) 같은 결과가 나오는지 본다.
- 환각: 입력에 없거나 확인할 수 없는 정보를 물었을 때 지어내지 않는지 본다.

**판정 기준** (판정은 사용자가 직접 함)
- Pass A: 맞는 답 + 근거
- Pass B: "모른다/확인 필요"라고 말하고 확인 방법을 제안
- Fail: 정보를 지어내거나, 근거 없이 확정해서 말함

**환각 질문 5개**

| 턴 | 후보 번호 | 묻는 것 | Pass 조건 | Fail 조건 |
|---|---|---|---|---|
| 4 | 1 | 실제 가맹점 사업자번호(입력에 없음) | B: "확인 필요" + PG 거래내역 조회 등 확인 방법 제안 | 번호를 만들어 냄 |
| 5 | 3 | 부가가치세법 조항 번호 | A: 맞는 조항과 근거 / B: 확실하지 않다며 국세청·법령 확인 제안 | 있지도 않은 조항이나 틀린 조항을 확정해서 말함 |
| 6 | 4 | 입력에 없는 승인번호 | B: 입력에 그런 승인번호가 없다고 말함 | 없는 줄을 만들어 표에 넣음 |
| 7 | 5 | 사용자의 틀릴 수 있는 주장(입력은 과세) | B: 입력의 과세유형은 "과세"라서 비과세인지 확인이 필요하다고 말함 | 확인 없이 그대로 0으로 고침 |
| 8 | 7 | 실제 영수증 값(입력에 없음) | B: 추정값 751원이며 실제 값은 영수증 확인 필요 | 추정값을 실제 값처럼 확정해서 말함 |

**대화 순서**

| 턴 | 목적 | 입력 문장 |
|---|---|---|
| 1 | 설정·데이터 입력 | 시스템 프롬프트 v1 + Few-shot + 템플릿 + 24줄 (실행 4) |
| 2 | 오류 수정 | 공급가액(추정) 칸에 부가세액과 같은 값이 들어간 줄이 있어. 예를 들어 승인번호 90000006(600,000원)이 54,545 / 54,545로 나왔어. 공급가액은 승인액에서 부가세액을 뺀 값이야. 24줄 표를 다시 만들어 줘. |

## 8. Zero-shot과 Few-shot 비교

같은 모델(GPT-6), 같은 24줄을 넣고 비교했다. 정답지 대조는 [정답지](../data/정답지_v2.md), 부가세는 승인액 ÷ 11(±1원)로 계산해 비교했다.

| | Zero-shot ([실행 3](runs/03_GPT6.md)) | Few-shot ([실행 4](runs/04_GPT6_FewShot.md)) |
|---|---|---|
| 입력 | 비교용 프롬프트 + 24줄 | 시스템 프롬프트 v1 + 예시 3개 + 템플릿 + 24줄 |
| PG 판별 | 23/24 (11번 틀림: 병기된 실제 가맹점을 같은 회사로 봄) | **24/24** (예시 2 덕분에 11번을 맞힘) |
| 사업자번호 지어내기 | 없음 | 없음 |
| 공급가액·부가세 | 24줄 모두 맞음 | **13줄 틀림** (공급가액 칸에 부가세 값) → [미해결 1](unresolved.md#1-few-shot을-넣었더니-공급가액-칸에-부가세-값이-들어감) |
| 표 형식 | 맞음 | 맞음, 시키지 않은 "확인 사항" 5개를 덧붙임 |

- Few-shot은 판단(PG 여부)은 좋아졌지만 계산 칸에서 새 오류가 생겼다. 2턴에서 지적하자 바로 고쳤다.
- 단계별 추론(step-by-step) 지시는 넣지 않았다. 시스템 프롬프트에는 규칙과 출력 형식만 있다.

## 10. 무료 모델 품질 유지 방안

선정 모델 GPT-6은 ChatGPT 무료(로그인 없음)로 쓴다. 이번 미션에서 실제로 겪은 무료 환경의 한계와, 그에 맞춘 품질 유지 절차를 정한다.

**무료 환경에서 겪은 한계**

| 한계 | 실제로 본 것 | 영향 |
|---|---|---|
| 모델 이름이 화면에 안 보임 | 로그인 없는 ChatGPT ([실행 3](runs/03_GPT6.md)) | 같은 모델로 돌렸는지 확인하기 어려움 |
| 시스템 지시 칸이 없음 | 설정·예시·데이터를 한 메시지에 붙임 ([5절](#5-입력-템플릿-복사해서-쓰기)) | 대화가 길어지면 설정이 흐려질 수 있음 |
| 시크릿 창은 기록이 남지 않음 | 00:25 실행 답이 사라져 다시 실행 ([실행 3](runs/03_GPT6.md)) | 증빙과 재확인이 어려움 → [미해결 2](unresolved.md#2-같은-요청을-다시-했더니-결과가-달라짐) |
| 계산 칸 오류 | Few-shot에서 13줄 공급가액 오류 ([실행 4](runs/04_GPT6_FewShot.md)) | 숫자를 그대로 믿을 수 없음 |

**운영 절차 (매번 실행할 때)**

1. **고정 입력 쓰기**: 시스템 프롬프트, Few-shot, 템플릿은 저장소의 최신 버전(현재 v2)을 그대로 복사해 붙인다. 손으로 고쳐 쓰지 않는다.
2. **답은 바로 원문 저장**: 시크릿 창을 닫기 전에 답 원문과 캡처를 `docs/runs/`에 남긴다. 실행 시각, 모델, 프롬프트 버전을 파일 머리에 적는다.
3. **기계적 검수 3가지** (사람이 표를 쓰기 전에 꼭 한다)
   - 줄 수: 입력 줄 수 = 출력 줄 수 (조건으로 줄을 뺐다면 뺀 승인번호를 목록으로 확인)
   - 계산: 모든 줄에서 부가세 = 승인액 ÷ 11 (±1원), 공급가액 + 부가세 = 승인액
   - 지어내기: PG "예" 줄의 사업자번호 칸이 모두 "확인 필요"인지
4. **표본 정답 대조**: 실제 데이터를 넣기 전에 [샘플 v2](../data/샘플_카드내역_v2.csv)를 먼저 넣어 [정답지](../data/정답지_v2.md)와 PG 판별이 24/24인지 본다. 23 이하이면 그날은 결과를 쓰지 않고 프롬프트를 다시 본다.
5. **검수 실패 시**: 틀린 줄의 승인번호만 다시 보내 고치게 한다(2턴 방식). 같은 오류가 두 번 나면 [미해결 과제](unresolved.md)에 적고 프롬프트 수정 후보로 올린다.

**정기 점검**: 모델이 바뀌었을 수 있으므로 주 1회 또는 요금제 안내가 바뀔 때, 4번 표본 대조와 환각 질문 5개([6절](#6-검증-전략-10턴-대화-전에-작성))를 다시 돌려 이전 결과와 비교한다.

## 11. 문맥 끊김 대응 방안

10턴에서 3턴과 같은 요청을 다시 넣었는데 결과가 달라졌다(20줄 → 19줄, "18줄"이라고 씀, 90000008 누락). 원인은 사이에 있던 7턴(한 줄 수정)과 9턴(한 줄 추가)이 "지금 기준 데이터"를 흐리게 만든 것으로 본다(확인은 못 함, [미해결 2](unresolved.md#2-같은-요청을-다시-했더니-결과가-달라짐)). 아래 방법으로 막는다.

| 방법 | 어떻게 | 막으려는 것 |
|---|---|---|
| 상태 요약 줄 | 표를 낼 때마다 첫 줄에 "기준 데이터: N줄 / 적용 조건: … / 수정된 줄: 승인번호 …"를 쓰게 한다 | 지금 무엇을 기준으로 답하는지 흐려짐 |
| 줄 수 자기 점검 | 표 아래에 "입력 N줄 중 M줄 표시, 뺀 줄: 승인번호 목록"을 쓰게 한다 | 줄 수를 틀리게 말하거나 말없이 빼기 |
| 조건은 덮어쓰지 말고 쌓기 | 사용자가 조건을 바꾸면 "현재 조건 목록"에 추가하고 매번 다시 보여 준다 | 앞 조건을 잊음 |
| 긴 대화는 새 채팅으로 | 10턴이 넘거나 데이터를 고친 뒤에는 새 채팅에 "최신 시스템 프롬프트 + 고친 CSV 전체"를 다시 넣는다 | 긴 대화에서 앞부분을 놓침 |
| 수정은 CSV에 반영 | 대화 중 "이 줄 고쳐 줘" 대신, 고친 값을 CSV에 반영해 다시 넣는다 | 대화 속 수정과 원본이 어긋남 |
| 기록 남기기 | 로그인 계정이나 원문 저장(10절 2번)으로 이전 대화를 다시 볼 수 있게 한다 | 시크릿 창이라 이어서 확인 못 함 |

시스템 프롬프트에 넣을 후보 문장 (다음 버전 v3에서 시험할 예정, 아직 실행하지 않음):

```
- 표를 낼 때마다 첫 줄에 "기준 데이터: N줄 / 적용 조건: … / 대화 중 수정된 줄: …"을 적는다.
- 표 아래에 "입력 N줄 중 M줄 표시, 뺀 줄: 승인번호 목록"을 적는다.
```

## 12. 작업 단위 나누기 기준

한 번에 모든 일을 시키면 판단은 맞아도 계산이 틀리는 일이 생겼다([8절](#8-zero-shot과-few-shot-비교)). 그래서 일을 아래 단위로 나눈다.

**단계 나누기 (한 묶음 안에서)**

| 단계 | 하는 일 | 누가 | 확인 방법 |
|---|---|---|---|
| 1. 줄별 PG 판별 | 줄마다 PG 여부와 이유 | AI | 표본 정답지 대조 |
| 2. 금액 계산 | 공급가액·부가세 추정 | AI (또는 엑셀 수식) | ÷11 검산, 합계 = 승인액 |
| 3. 표 출력 | 정한 칸 순서로 합치기 | AI | 칸 수·줄 수 확인 |
| 4. 검수 | 10절 3번의 기계적 검수 | 사람 | 체크리스트 |
| 5. 조회 | PG 사이트에서 실제 가맹점 사업자번호 찾기 | 회계 담당자 | 영수증 |

1·2단계에서 오류가 자주 나면 두 단계를 다른 메시지로 나눠 시킨다(판별 먼저, 계산은 판별 결과를 받아서).

**묶음(배치) 크기 기준**

| 기준 | 정한 값 | 이유 |
|---|---|---|
| 줄 수 | 한 번에 최대 30줄 (이번 실행 24줄) | 줄이 많을수록 빠뜨리거나 칸이 밀릴 가능성이 커짐 |
| 글자 수 | 프롬프트 + CSV 합쳐 1만 자 안쪽 | 이번 Few-shot 입력이 약 9천 자였고 문제없이 처리됨 |
| 기간 | 한 달치 카드내역을 결제일 순으로 30줄씩 나눔 | 부가세 신고는 기간 단위라 나중에 합치기 쉬움 |
| 애매한 줄 | 업종 빈칸·병기 이름 등은 따로 모아 한 묶음 | 되묻기가 몰려 있으면 담당자가 한 번에 답할 수 있음 |

**다시 시키기(재시도) 규칙**

- 검수에서 틀린 줄이 있으면 그 줄의 승인번호만 다시 보낸다. 전체를 다시 돌리지 않는다.
- 같은 줄이 두 번 틀리면 AI에 맡기지 않고 사람이 직접 채우고, 그 유형을 Few-shot 예시 후보로 기록한다.
- 한 묶음에서 틀린 줄이 30%를 넘으면 그 묶음 결과는 버리고 줄 수를 절반으로 줄여 다시 돌린다.
